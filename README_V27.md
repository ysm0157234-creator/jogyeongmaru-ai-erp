# v27 .hwp "파일이 손상되었습니다" 수정

## 증상

v26 배포 후 실제로 생성된 `.hwp`를 한글에서 열면 "파일이 손상되었습니다"가 떴다.
제 손으로 만든 테스트 파일들은 전부 정상이었다.

## 원인 — 길이 1짜리 빈 문단

원본 서식(레퍼런스 `.hwp`)의 문단 길이 분포를 보면 **길이 1인 문단이 하나도 없다**(최소 2자).

```
원본 레퍼런스 문단 길이(짧은 순): [2, 3, 3, 4, 4, 4, ...]
손상본 [40] '⑨검역합격 서류의 발급번호' 값 = 1자   ← 문단끝 표시 \r 하나뿐
```

**검역합격번호가 비어 있어서** `{{검역합격번호}}`가 빈 문자열로 치환됐고, 그 문단에는
문단끝 표시만 남았다. 한글은 이 상태를 손상으로 판정한다.

테스트에서 안 걸린 이유: 내가 만든 샘플은 모든 필드가 채워져 있었다. 서버에서는 Drive에
검역합격증이 없어 빈 값이 들어갔다.

### 수정

치환 결과에 실제 글자(코드 32 이상)가 하나도 없으면 공백 한 칸을 넣는다.

## 함께 바로잡은 것 — v26에서 잘못 짚었던 진단

처음에는 `PARA_CHAR_SHAPE`(글자모양)·`PARA_LINE_SEG`(줄정보)의 **글자 위치가 새 본문 길이를
넘는 것**이 원인이라고 보고, 넘는 항목을 제거하는 코드를 넣었다. **둘 다 틀렸다.**

1. **위치 초과는 문제가 아니다.** 정상적으로 열리는 파일에도 위치 초과가 있었다.
   한글은 배치 정보를 다시 계산한다.

   ```
   정상 열림 [ 99] 12자인데 글자모양이 37번째를 가리킴
   정상 열림 [101]  2자인데 줄정보가 43번째를 가리킴
   ```

2. **항목을 지우면 오히려 깨진다.** `PARA_HEADER`가 두 레코드의 **항목 개수를 따로 기록**하고
   있어서, 항목만 지우면 개수가 어긋난다.

   ```
   잘못된 수정본 → 개수 불일치 5개  [('줄개수', 2, 1), ('모양개수', 2, 1), ...]
   ```

→ 해당 코드를 제거하고, 두 레코드는 손대지 않는다. 코드에 이유를 주석으로 남겼다.

확인했다.**

## 진단 과정에서 확인한 사실 (다음에 참고)

- 레코드 파서는 본문·DocInfo 모두 **바이트 단위 왕복 일치**한다.
- OLE 스트림 비교 결과, 의도한 3개(`BodyText/Section0`, `BIN0005`, `BIN0006`)만 바뀐다.
  `DocInfo` / `FileHeader` / `PrvText` / `HwpSummaryInformation` 등은 그대로다.
- `DocInfo`의 캐럿 위치(문단 ID 107, 글자 위치 8)는 손대지 않아도 무방하다.
- 문단 길이가 길어지는 것 자체는 문제가 없다(원본에도 422자 문단이 있다).
